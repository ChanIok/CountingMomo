## Project Overview

CountingMomo (盘点吧大喵) is a Windows-only collection status scanner for the game "Infinity Nikki" (无限暖暖). It automates compendium scanning (美鸭梨 → 博物图鉴 → 检索) across 27 categories by switching categories, scrolling pages, and detecting card ownership states to export structured boolean (0/1) arrays paired with game item database IDs.

Technology Stack: Pure C++23 native Win32 desktop application with Direct2D, DirectWrite, DirectComposition, and Windows.Graphics.Capture (WGC) + Direct3D 11.

## Domain Invariants

- **Compendium Slots**: Slot positions are fixed per version. Unowned items appear as question mark cards (recorded as `0`) and preserve their slot positions.
- **Output Format**: JSON mapping English category keys to `[0, 1]` arrays ordered row-by-row, left-to-right from the first item.
- **Sequence Integrity**: Scanning must maintain complete sequence without skipping unrecognized items. Question marks count as 0; overlapping rows between page scrolls are deduplicated.
- **Atomic Publishing**: The GUI only publishes completely successful scans across all categories. Aborted or partial scans are discarded, never saved or mixed into formal results.
- **Minimal Diagnostics**: Diagnostics (`data/diagnostics/<timestamp>/report.json` and `failure.png`) are written only when a scan task fails or terminates with cleanup warnings. Clean success and normal user stop create no diagnostic files.

## Architecture

### Single-Process Native Model
The application runs as a single native Win32 process with clear thread responsibilities:
- **Main UI Thread**: Runs the Win32 message loop, renders native Direct2D/DComp UI (main panel and transparent status overlay), and handles user interactions.
- **Scan Task Thread**: A single synchronous worker thread executing the multi-category scanning lifecycle, game window resizing, navigation, and frame evaluation.
- **WGC Frame Callback**: Frame-arrived events only signal an auto-reset synchronization event; they never fetch frames or invoke Direct3D directly.

### C++ Directory & Namespace Architecture
The codebase uses self-contained C++23 headers and implementation files (`.hpp + .cpp`) without precompiled headers:

- `core::*` — foundational application infrastructure:
  - `core::state` (`app_state.hpp`): centralized root state holding subsystem states via `std::unique_ptr`
  - `core::initializer` & `core::shutdown`: explicit application-level lifecycle orchestration
  - `core::startup`: single-instance named mutex check and UAC administrator elevation handling
  - `core::message` & `core::i18n`: structured error model and compile-time checked dual-language localization
- `features::*` — business logic and hardware integration:
  - `features::scan`: worker job management (`job`), pagination loop (`scan`), vision/card detection (`vision`), layout geometry (`layout`), cancellation flags (`control`), diagnostics logging (`diagnostics`), and end-to-end orchestration (`usecase`)
  - `features::capture`: WGC capture session, D3D11 device/staging texture management, and GPU stability compute shader
  - `features::navigation`: compendium category directory, navigation state machine, and icon matching
  - `features::window`: game window detection, temporary 1440x5760 borderless resize, and window restore
  - `features::result`: completed scan results storage, JSON serialization, and clipboard operations
  - `features::settings`: persistent user settings in `data/settings.json`
- `ui::*` — native Win32 / Direct2D presentation:
  - `main_window`: main panel layout, painting, button actions, and notifications
  - `status_window`: non-activating right-bottom overlay on the game monitor
  - `theme`, `composition`, `backdrop`, `button`, `drawing`: custom D2D/DComp controls, light/dark themes, and system backdrop effects
- `utils::*` — shared utilities: `file`, `image` (WIC PNG), `string` (UTF-8 <-> UTF-16), `clipboard`
- `vendor/**/*.hpp` — external dependency include facades (standard library, Win32 SDK headers, OpenCV, reflect-cpp). External angle-bracket includes are restricted to `src/vendor/`. SDK facades under `vendor/windows/` map 1:1 to physical SDK headers.

### Design Philosophy
- **POD Structs + Free Functions**: Plain data structs with behavior implemented as free functions. No OOP inheritance hierarchies.
- **Centralized State**: `core::AppState` is the single root state. Subsystem states are owned via `std::unique_ptr` with forward declarations in headers. Functions take `AppState&` explicitly rather than threading ephemeral context objects through calls.
- **Usecase Orchestration**: Cross-module workflow coordination belongs in `usecase.hpp/.cpp` (e.g. `features::scan::run_scan`).
- **Explicit Lifecycle**: Application initialization and teardown are explicitly sequenced in `core::initializer` and `core::shutdown`, ensuring tasks stop, UI windows destroy, and COM revokes cleanly before state destruction.

### Key Patterns & Invariants
- **GPU Stability Verification**:
  Scanning automates the game at 1440x5760 borderless vertical. After input (category click or scroll), the scan thread waits on frame arrival, compares the WGC texture against a single GPU reference texture using a D3D11 compute shader over the fixed `stability_rect` (excluding game UI animations). A frame is declared stable after remaining unchanged for `stable_seconds` (0.25s) measured by QPC source time. Only the verified stable frame is staged and read back to CPU as a `cv::Mat`.
- **Threading & Synchronization**:
  The worker thread posts `latest` progress and `pending` final outcome under a mutex, notifying the UI thread via `PostMessageW`. The UI thread consumes snapshots without touching active scanning buffers. Cancellation (via the configurable stop key, default F10, or UI stop button) wakes waiting frames immediately.
- **Error Handling & Diagnostics**:
  Predictable failures use `std::expected<T, core::Error>`. User-facing errors show only high-level translatable messages via `core::i18n::wide(state, failure.message)`. Structured diagnostic details (`report.json` + `failure.png`) are written only when an actual failure or window-restore warning occurs.
- **Single-Instance & Elevation**:
  Manifest specifies `asInvoker`. The app first verifies the `Local\CountingMomo.SingleInstance` mutex; if an unprivileged instance is started without existing instances, it elevates via `runas`. Subsequent invocations activate the running instance's window without prompting for UAC.
- **Portable Data Storage**:
  User data resides strictly in `data/` adjacent to the executable (`data/settings.json`, `data/diagnostics/`). AppData is not used.
- **Localization (i18n)**:
  `src/locales/zh-CN.json` and `en-US.json` compile into `src/core/i18n/generated/texts.hpp`. UI boundary code looks up wide strings via `core::i18n::wide(state, key, args...)`.

## Code Generation Scripts
These scripts must be re-run when their corresponding source files change:
- `node scripts/generate-locales.js` (or `pnpm run generate:locales`): Rebuilds `src/core/i18n/generated/texts.hpp` after editing locale JSON files.
- `node scripts/format-cpp.js` (or `pnpm run format:cpp`): Formats all C++ source files with clang-format.

## Naming & Code Conventions
- **Namespaces / Functions / Files**: `snake_case` (e.g., `features::scan`, `wait_stable_frame()`, `usecase.cpp`).
- **Types**: `PascalCase` (e.g., `AppState`, `ScanProgress`, `Outcome`).
- **Include Order**: In `.cpp`, matching header first, followed by `vendor/std.hpp`, other vendor facades, then project headers.
- **Comments**: Describe intent and constraints (why), never narrate implementation steps or past changelogs.
